- [ ] `p2` `SyncStore.journalSince` checks the all-complete gate and scans entries in two statements, each with its own READ COMMITTED snapshot. That breaks two things. (1) **Gate leak:** the member list it reads can still be all complete when Bob unmarks and pushes entry E, and then the scan includes E. Both the `sync.journal` query and `sync.onJournalChange`'s startup backfill go through here, so either one can return E while Bob is incomplete. (2) **Skipped entry:** say an admin adds member X between the two statements (only possible before the group is marked ready), X pushes entry N, and an existing member then commits N+1. The scan filters on the old member list, so it returns N+1 without N, the cursor passes N, and every read once X completes resumes past N. Fix: run `journalSince` in one REPEATABLE READ transaction, so the gate and the scan see the same snapshot. `SyncStore.#tx` forwards only the callback today, so it has to pass `{ isolationLevel: "repeatable read" }` through. Since #248 a group's ids commit in order, so if E or N+1 is in the snapshot, the unmark or X's row is too, and the gate fails instead. Test, on real Postgres since it needs separate connections: pause `journalSince` after its member read, with a `Database` wrapper like `holdCommit` in `sync.journal-subscription.integration.test.ts` that passes the transaction options through. While it's paused, unmark Bob and commit a push E from him. Then release it and expect a result without E: the snapshot predates both writes. Also expect a fresh `sync.journal` read to fail with `PRECONDITION_FAILED`, and for the subscription, expect E to be missing from the backfill and its live batch to be rejected by the live gate (entry below). Found in review of #248.
- [ ] `p2` `sync.onJournalChange` checks the all-complete gate only when it opens. After that it streams every new entry in the group. So if a member unmarks completion, an open `/results` stream keeps delivering new answers while the group is incomplete. `addPerson` can trigger the same leak, but only in a group not yet marked ready. The app closes the stream itself for viewers who are still complete, because `resolveRoute` moves them from `/results` to `/waiting`. A modified client can keep it open, though, and read answers before everyone is done, which gets around the server-side gate (`design/sync.md` § Blind matching). Fix: before each live batch, check the gate again, after the batch's entries have committed. If it fails, end the stream with `PRECONDITION_FAILED`. That authorizes every entry against a status at least as new as the entry. An unmark that lands between the check and the yield still lets that one batch through, but everything in it was readable when the check ran. Accept that window, or coordinate with completion changes if the guarantee has to hold at the moment of the yield. An unmark and re-mark between two batches isn't a leak, since a fresh subscriber could read the same entries by then. A `groupEvents` listener would close idle streams sooner, but on its own it can miss a quick unmark/re-mark. The startup backfill has its own gap; see the `journalSince` entry above. Test: consume the backfill, unmark Bob, have Bob push and await the commit, then assert the stream rejects with `PRECONDITION_FAILED` and yields nothing, and that a fresh subscribe also fails.
